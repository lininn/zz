# 任务：群组任务自动流转（PM 计划确认 → 自动分配接力）

用户需求原话：「应该任务自动流转。只有我要求的项目经理出完计划后找我确认，其他由项目经理自动分配流转。」

## 目标交互

1. 用户 @项目管理 提需求 → PM 输出**计划**（拆解 + 指定成员）→ **停下等用户确认**（任何模式下 PM 计划都必须人工批准，这是唯一强制人工点）。
2. 用户点「批准计划」→ PM 计划里的分配**自动派工**给成员 → 成员完成 → 成员输出中的交接（如交回 PM 汇总、转评审）**自动继续流转** → 直到无交接 / 预算耗尽 / 失败熔断。
3. 全程消息流可见：「A → B 自动派工」徽标；用户可随时暂停（群级开关）或取消执行。
4. 群组接力模式三档（群设置）：`manual`（现状：所有派工人工点）、`semi`（前 K 跳自动后转人工，K 可配默认 2）、`auto`（确认计划后全自动，受预算熔断）。

## 技术方案（受控交接，不扫描自由文本）

- **Agent 侧交接通道**：派工 prompt 中注入约定——执行 Agent 在**最终回复**里用结构化标签声明交接：
  `<crew-handoff>{"to":"<memberName>","objective":"...","context":"..."}</crew-handoff>`（to 必须是群成员名）。
  服务端在执行完成回调处**只解析最终回复中的该标签**（多次出现取最后一个；解析失败/无标签 = 流转结束，回群板等待）。正文其他 @ 仍不触发。
- **数据**：migration v7——`agent_crew_groups` 加 `relay_mode`('manual'|'semi'|'auto') 与 `relay_auto_hops`；`agent_crew_executions` 加 `root_request_id`、`hop`（流转链归属，用于预算与循环熔断）。
- **服务端**：执行完成（finish 成功）时解析 handoff → 按群组 relay_mode 决策：
  - manual：生成「待批准交接」卡片（新消息类型或 execution 侧状态），用户点批准才派工；
  - semi：hop ≤ K 自动，之后转待批准；
  - auto：自动派工，直到无 handoff。
  - **硬熔断**（任何模式生效）：单链 hop ≤ 8、单链总耗时上限（默认 30 分钟，群可配）、同一 (root, to, objective 指纹) 重复交接拒绝、目标成员 runtime 不可用即熔断回群板、恢复未决状态下不自动流转。
  - 幂等：自动派工沿用 send 幂等键（rootRequestId + hop + to）。
- **PM 计划确认**：PM 执行完成后若其最终回复含 handoff，无论模式先置会话/链状态 `awaiting_user_approval`，UI 出**计划确认卡片**（显示计划摘要 + 分配清单，按钮：批准并开始 / 拒绝）。批准 = 系统按计划派工并进入自动流转。后续成员间的流转不再人工确认。
- **UI**：
  - 群设置（编辑群/详情）加接力模式选择（manual/semi/auto + K 值、hop/时长预算展示）；
  - 群聊消息流：交接卡（待批准：显示目标+目标内容+批准/拒绝按钮；自动派工：A→B 徽标）；
  - 计划确认卡片置顶醒目；
  - 熔断/预算耗尽时群板系统消息说明原因。
- i18n zh/en 同步。

## 硬约束

- 复用现有数据层与幂等键体系；不建第二套执行通道。
- 恢复未决（recovery_required）会话在确认前禁止自动流转（复用现有阻塞）。
- 不重放已创建 task 的输入（沿用「绝不重放」）；权限请求仍走现有人工批准，不自动放行。
- migration 走本仓库体系并更新 checksum；旧群默认 relay_mode='manual'（行为不变）。
- 架构策略、≤400 行、不 commit、不动 `apps/zcode-cli` 未提交文件。
